# Serenity - compiler frontend and interpreter v0.7

Serenity is a statically typed compiled language with an AOT compiler, a
bytecode interpreter, and a planned tracing JIT. This repository currently
contains the frontend, bytecode generator, and first interpreter.

## Current components

- **Lexer v0.1:** tokenization and lexical diagnostics.
- **Preprocessor v0.2:** `%include` expansion, relative path resolution,
  include-once behavior, cycle handling, and source-origin mapping.
- **AST v0.3:** syntax tree model with source spans.
- **Parser v0.4:** recursive-descent parser and precedence-aware expressions.
- **Semantic analysis v0.5:** name/type resolution, signature checking,
  mutability and control-flow context checks.
- **Bytecode generator v0.6:** fixed-width stack instructions, constants,
  global/local slots, function calls, control flow, structs/enums, source spans,
  and disassembly.

- **Interpreter v0.7 (`sninterp`):** executes generated bytecode directly with
  call frames, typed runtime values, structs/enums, runtime diagnostics, and
  execution statistics.

The interpreter does not link LLVM. `snjit` will later execute the same bytecode,
profile hot loops, and compile traces to native machine code. The `serenity` AOT
executable and LLVM backend remain future milestones. Bytecode is generated in
memory for now; `.sbc` serialization is not implemented.

## Build and test

```sh
cmake -S . -B build
cmake --build build -j
ctest --test-dir build --output-on-failure
```

On macOS, CMake prefers the Homebrew LLVM toolchain when it exists:

```cmake
set(CMAKE_C_COMPILER "/opt/homebrew/opt/llvm/bin/clang")
set(CMAKE_CXX_COMPILER "/opt/homebrew/opt/llvm/bin/clang++")
```

On other systems, or where that Homebrew prefix does not exist, CMake uses the
system's normal compiler discovery.

## Run a Serenity program

```sh
./build/sninterp examples/interpreter_demo.sn
```

The executable preprocesses, tokenizes, parses, semantically analyzes,
generates bytecode, and executes the program. The current `.sbc` serialization
and bytecode loader are not implemented; bytecode is held in memory.

## Bytecode generation API

Run the lexer, parser, and semantic analyzer first. Generate bytecode only when
both lexing/parsing and semantic analysis succeed:

```cpp
#include "serenity/bytecode/generator.hpp"
#include "serenity/lexer/lexer.hpp"
#include "serenity/parser/parser.hpp"
#include "serenity/semantic/analyzer.hpp"

#include <utility>

serenity::Lexer lexer(source);
auto lexed = lexer.tokenize();
if (!lexed.ok()) {
    // Report lexed.errors.
}

serenity::parser::Parser parser(std::move(lexed.tokens));
auto parsed = parser.parse();
if (!parsed.ok()) {
    // Report parsed.errors.
}

serenity::semantic::SemanticAnalyzer analyzer(*parsed.program);
auto checked = analyzer.analyze();
if (!checked.ok()) {
    // Report checked.errors.
}

serenity::bytecode::BytecodeGenerator generator(*parsed.program, checked.model);
auto generated = generator.generate();
if (generated.ok()) {
    const std::string listing = serenity::bytecode::disassemble(*generated.module);
}
```

The AST must remain alive and unchanged while its `SemanticModel` is used.

To execute the generated module through the C++ API:

```cpp
#include "serenity/interpreter/interpreter.hpp"
#include <iostream>

serenity::interpreter::Interpreter vm(*generated.module, std::cout);
auto execution = vm.run();
if (!execution.ok) {
    // Inspect execution.error and execution.stats.
}
```

See `docs/BYTECODE_v0.6.md` for instruction layout, stack effects, function
calling convention, defaults, and current limitations. See
`docs/INTERPRETER_v0.7.md` for runtime behavior, CLI usage, diagnostics, and
execution statistics. Earlier milestone notes remain in `docs/`.
