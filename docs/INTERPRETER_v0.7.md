# Serenity Interpreter v0.7 (`sninterp`)

## Purpose

`sninterp` executes Serenity bytecode directly. It is independent of LLVM and
uses the bytecode generated by the v0.7 frontend. The future `snjit` executable
will use this same bytecode representation, initially interpreting it and
later compiling hot traces to native machine code.

The v0.7 command-line tool accepts Serenity source files. It runs the complete
frontend pipeline in-process:

1. `%include` preprocessing;
2. lexical analysis;
3. parsing;
4. semantic analysis;
5. bytecode generation;
6. bytecode execution.

The generated bytecode currently remains in memory. A serialized `.sbc` module
format and bytecode loader are not part of v0.7.

## Build

```sh
cmake -S . -B build
cmake --build build -j
ctest --test-dir build --output-on-failure
```

The interpreter library and executable do not link LLVM.

## Usage

```sh
sninterp examples/interpreter_demo.sn
```

The command prints the output produced by Serenity's `print()` and `println()`
functions. The process exit status is the low byte of an integer returned by
Serenity's `main`; runtime or frontend errors produce a nonzero process status.

## Runtime representation

The runtime `Value` type stores one of:

- null (`std::monostate`);
- signed 64-bit integer;
- 32-bit float;
- 64-bit double;
- boolean;
- UTF-8 string;
- stream handle (`stdin`, `stdout`, or `stderr`);
- enum value (enum descriptor and member indices);
- shared struct instance reference.

Struct values use shared references. Copying a struct variable copies the
reference, so aliases refer to the same underlying instance. This supports the
language's nullable struct values and automatic-memory-management direction.

Struct construction allocates an instance and initializes every field from its
constant default, or from the language default when no explicit default exists.
`GET_FIELD` reads a field. `SET_FIELD` mutates the referenced instance; static
mutability enforcement remains the semantic analyzer's responsibility.

## Call frames and stacks

The interpreter has a shared operand stack and a separate vector of call frames.
Each call frame records:

- the function index;
- the next instruction index;
- the operand-stack base for the call;
- its local-slot values.

Arguments are evaluated left-to-right by the bytecode generator. `CALL` removes
the argument values from the caller's operand stack and places them into the
callee's initial local slots. Parameters occupy local slots beginning at zero.
A non-void `RETURN` pushes its result onto the caller's operand stack. A `Void`
return is used by the synthetic global initializer and produces no stack value.

The global slots are initialized to language defaults before the synthetic
global initializer executes. The interpreter then invokes the module entry
function (`main`).

## Standard I/O

Bytecode v0.7 provides `PUSH_STREAM`, `STREAM_READ`, and `STREAM_WRITE`. The
interpreter accepts input, output, and error streams through its constructor,
so tests and embedding applications can redirect all three independently.
`STREAM_READ` reads one line from `stdin` and returns null at EOF.

## Runtime checks

The interpreter validates instruction operands, constant indices, local/global
slots, function indices, argument counts, field indices, and runtime value types.
It reports failures such as:

- integer division/remainder by zero;
- signed integer arithmetic overflow;
- invalid shift counts or overflowing left shifts;
- null struct field access;
- operand-stack underflow;
- malformed jump targets;
- invalid bytecode type/value combinations.

Floating-point arithmetic follows the host's IEEE floating-point behavior,
including infinities and NaN where produced by operations such as division by
zero.

`InterpreterOptions` provides two execution safety limits:

- `maxInstructions` defaults to 100,000,000 executed instructions; zero disables
  the instruction limit;
- `maxCallDepth` defaults to 1,024 active frames.

## Diagnostics and statistics

Every runtime error records the function, instruction index, and original AST
source span associated with the instruction. The CLI maps expanded-source
locations back through the preprocessor's source map to the real `.sn` or
`.snh` file.

`ExecutionResult` exposes runtime statistics:

- executed instruction count;
- function-call count;
- peak operand-stack depth;
- peak call-stack depth.

These counters will also provide useful inputs for the future `snjit` hot-code
profiler and for comparing interpreter execution with warmed-up JIT execution.

## API

```cpp
#include "serenity/interpreter/interpreter.hpp"

#include <iostream>

serenity::interpreter::Interpreter vm(module, std::cout);
auto result = vm.run();
if (!result.ok) {
    // Inspect result.error.
}
```

The `BytecodeModule` must remain alive and unchanged for the lifetime of the
interpreter.

## Current limitations

- No `.sbc` serialization or loader.
- No tracing profiler or JIT compilation; those belong to `snjit`.
- No tracing garbage collector yet. Struct instances currently use
  `std::shared_ptr`; reference cycles can therefore retain objects until a later
  garbage-collector milestone replaces this interim ownership strategy.
- Struct equality currently compares object identity, not field-by-field value.
- No arrays, indexing, closures, external functions, or native FFI.
- `print()` and `println()` accept one printable primitive argument, as defined by
  the current semantic analyzer.
